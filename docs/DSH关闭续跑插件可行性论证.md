## 0. 结论（先看这段）

| 需求段 | 判定 | 一句话理由 |
|---|---|---|
| ① 提供关闭 DSH 的入口 | **可行，成本低** | 宿主进程内插件可以让自己的进程退出；Windows 与社区都有现成实现可抄。⊖ （原文此处写"平台全包无关闭信号处理器，所以优雅这一半必须插件自己补"——复验推翻：平台有处理器与整套关闭链路，插件要做的是**把关闭请求投递到它**，见复验文档 §1 / §1.1） |
| ② 关闭前记录正在运行的 Agent 会话 | **基本已天然具备，真缺口只有两点** | 会话日志本就追加写 + 每批落盘；缺的是 ①关闭前的**耐久屏障落盘**（没落盘的事件崩溃即丢）②一份**活跃会话意图清单**（谁在跑、跑到哪一步）。⊖ （复验：落盘这一半平台在拆卸 effect 里做了，缺的只剩意图清单） |
| ③ 下次启动自动继续所有会话 | **技术上可行，语义上危险，必须收窄** | 平台的目标原语 + 投递消息就能续跑；但平台**刻意**把"是否继续"设成人类显式动作（恢复后目标处于未授权态），且无人时的工具审批按失败关闭 |

**一句话总评**：这个需求的真身不是"记录会话"（平台早就在记），而是**「给宿主一个体面的退出仪式」＋「给下一次启动一个接管点」**。前者有真实价值（平台自己没做），后者要收窄成"白名单 + 串行 + 有预算"，否则会把一台无人看管的机器变成并发写盘的现场。

**最大的结构性事实**（决定架构）：**插件活在宿主进程里，宿主一死插件也没了。** 所以"下次启动自动继续"这件事**不可能由关闭时的插件完成**，只能由**下一次启动时的宿主**完成；而"下次启动"本身由宿主之外的机制触发（Windows 上是启动文件夹里的一个快捷方式）。⇒ 需求天然分成"宿主内关闭半区"和"启动接管半区"，两半通过一份磁盘清单握手。

## 1. 平台能力实测（证据基线）

所有结论来自已安装的平台包源码，路径基址为运行实例所加载的那份包目录（下称 `<pkg>`）。

### 1.1 会话是怎么"跑起来"的

- 会话列表里的"在跑"字段的**唯一口径**是「有活 agent 且状态为 running」：
  - 会话控制器：`running: this.ctx.agents.get(session.id)?.status === "running"`
  - 类型定义处同口径；agent 运行时类型里 `AgentStatus = 'idle' | 'running'`
- **打开一个会话 = 让宿主恢复一个 agent**：控制器里"点开会话"与"起一个能干活的后台会话"走的是同一条通道。
- 插件可用的驱动面：
  - 枚举活 agent（`list` / `get(id)` / `roots()`）
  - 在持久化会话上重建 agent（`resume({ resumeSessionId, agentOptions, setup })`）
  - 投一条下一轮消息并唤醒驱动（`followup({ content, source })`，这就是"继续"）
  - 等静默（`await whenIdle()`）
  - 事件族：agent 的创建 / 结束 / 状态 / 回合收尾 / step 之前（见 agent 包 README）
- ⇒ **"记录正在运行的会话"在宿主侧是一个常数级调用**：枚举一次即可拿到活 agent 集合与状态，不需要扫盘、不需要解析日志。

### 1.2 会话日志早就落盘了（所以"记录"不是重点）

- 后端：每会话一个目录的 jsonl + zstd（实测存在，18 个项目目录）。
- 耐久语义（后端 README）：**每个追加批次在 resolve 前就 fsync**；已提交前缀永不改写；崩溃只影响最后一个未闭合回合；残尾按规则截断或补全。
- **真缺口**：写盘是"路由缓冲 + 固定批窗"的，**缓冲里还没追加的事件在崩溃中直接消失**。官方类型声明原话："flush, and never existed if the process crashes before that."
- 可用的落盘入口有两个层次：会话级（注释写明这是 **"THE flush entry point"**）与全量（"Flush every active write handle in one durability barrier"）。
- ⇒ **`关闭前落盘` 是本次需求里唯一"平台自己不做、且不做会丢东西"的动作**，也是"优雅关闭"相对"直接杀进程"的全部意义所在。
  ⊖ （复验修正：平台在拆卸 effect 里**会**逐会话落盘，见复验文档 §2；这条从"必需"降级为"冗余保险"）

### 1.3 硬杀会留下什么（别把它想得太糟，也别想得太好）

- **不会留下写死锁**：跨进程写租约是内核锁（Windows 上是命名内核信号量），持有者的句柄关闭即释放，**包括进程死亡的场合**。⇒ 硬杀不会导致下次开不了该会话。
- **会留下一个未闭合的回合**，读侧补合成事件收尾：工具没开始 / 工具结果未知（补一条"You can't tell whether it happened"）。
  也就是说：**续跑时模型会看到"上一次工具结果未知，请自行决定要不要重做"**。这既是有用的信号，也是"重复执行副作用"的来源。
- **子进程不会变孤儿**：Win32 侧用作业对象且带"句柄关闭即杀成员"的旗标，宿主句柄一关成员进程全终止。⇒ 关闭时正在跑的子进程会一起被杀，**不会**在后台偷偷继续写盘。这是好消息，但"写到一半的文件"仍然存在。

### 1.4 平台**没有**提供的东西

- ⊖ **（复验推翻本条结论，原文保留如下）** 原文称"全平台 0 个关闭信号处理器，所以终止信号即硬杀、没有优雅退出路径可选"。
  **复验实测**：宿主启动引导段内即有处理器（全量 grep 命中 19 处，其中宿主 2 处），收到关闭信号事件后会
  `await fiber.dispose()` 整棵树（含持久化落盘）并在 5 秒上限内退出 —— 平台有自己的关闭链路。
  **但复验又实测了另一件事**（2026-10-12）：把该信号"发给本进程"是**进程级强杀**，处理器不会跑
  （真子进程 `exit=1`、监听器从未被回调）⇒ **"投递到平台"这件事仍必须由插件负责**，原文"要体面关闭只能插件自己做"的
  结论方向因此**部分成立**：插件要做的不是"自己造一套关闭仪式"，而是**把关闭请求交到平台的处理者手里**。
- **没有宿主级 shutdown 服务/路由**可注入（复验仍成立）。
- **客户端无法可靠关闭用户的标签页**（`window.close()` 受限）。社区插件的做法是"全屏遮罩 + 自动刷新页面"，关闭场景只能退化成"墓碑遮罩 +（可选）重新启动按钮"。

### 1.5 已经内置的"恢复上次会话"

浏览器端**已经持久化了"当前会话选择"**（本地存储里的一个键），配一套恢复/清除逻辑。
⇒ 宿主重启后刷新页面，**你上次看的那个会话会被自动重新打开**（宿主侧随之恢复）。
**缺口**：只记一个（当前），且**只恢复、不续跑**；当时在后台跑着的其它会话完全不在其中。

## 2. 已有实现盘点（先看有没有人做过）

### 2.1 社区先例（来源：插件 registry 缓存）

| 插件 | 能力 | 与本需求的关系 |
|---|---|---|
| `dsh-restart-fab` | "右下角一键**重启**按钮：全屏遮罩**原地重启进程**并自动刷新页面；无需启动脚本，跨平台" | **证明了①完全可行**：杀宿主 + 页面遮罩 + 自动重载，且不依赖外部启动脚本（自己重拉） |
| `dsh-auto-continue` | "请求中断自动续跑：网络、超时或**宿主崩溃**等非人为失败后自动发送「继续」，含错误分类、自适应退避、模板化继续文本、浏览器通知" | **覆盖了③的一大半**，但只作用于"当前正在看的那个会话且请求失败"，不负责关闭、不负责多会话 |
| `dsh-shutdown-after-task` | 任务完成后自动**关机**（Windows `shutdown`） | 语义不同（关操作系统，不是关 DSH），但说明"宿主侧主动终止"这一族插件是社区常规玩法 |

⇒ **用户的想法 ≈ restart-fab + auto-continue 的并集**，真正新增的只有两点：**"关闭"（而非重启）** 与 **"多会话"**。

### 2.2 现成可抄的三份"杀宿主 + 拉起"实现

| 位置 | 机制 |
|---|---|
| 插件市场的重启模块 | spawn 一个脱离的 helper → helper 等端口/握手 → 延时后让宿主退出 → helper 重启宿主；处理了 Windows 无控制台、端口占用等坑 |
| 既有的一次性重启助手脚本 | 延时 → 按进程号强杀 → 轮询端口释放 → 隐藏窗口重拉宿主 |
| 另一个自研插件的常驻看门狗脚本 | 端口不空则退出；否则重拉宿主，进程退出后延时重启（登记为计划任务） |

### 2.3 用户自己已有的插件（避免重复造轮子）

- `dsh-session-backup`（`<插件目录>`）：已把会话日志**增量镜像**到工作区的备份目录，带 7 项哈希校验与自愈。
  它解决的是**备份/取证**，不是"关闭前的耐久屏障"，但审计与恢复能力可直接复用。
- `dsh-absent-mode`（`<插件目录>`）：已接管"AI 提问而人不在"的场景（提问请求瀑布里抢先应答）。
  它的 README 明确写了"**工具审批不接管**" —— 这正是"无人值守续跑"最大的坑，用户自己踩过一次。

## 3. 现实约束（决定"关闭"能不能真的关掉）

- 宿主当时：一个 `node` 进程监听回环端口，浏览器侧 4 条长连接（记录时刻的读数；进程号会被复用，不作现状）。
- 启动路径：**启动文件夹**里的快捷方式 → 一个批处理 → `npx … web`（运行实例来自 npx 缓存路径，非全局安装路径）。
  该批处理末尾有 `pause`，所以**结束 node 后那个黑窗口不会自己消失**。
- 看门狗：安装脚本称会注册一个计划任务。**当时非提权查询未列出任何相关任务**，所以"看门狗此刻是否在跑"**尚未取证**。
- ⚠️ **冲突点**：若看门狗在跑，用户点"关闭 DSH"后可能被**自动重拉**，"关闭"形同虚设。
  ⇒ 设计上必须与看门狗达成协议（约定退出码 / 落一个"计划内关闭"标记文件，看门狗见到就不重拉），否则这个功能会当场失效。

## 4. 设计上真正难的三点（也是必须让用户拍板的三点）

### 4.1 "继续"是什么语义？

- **语义 A（只恢复界面）**：下次启动按清单把会话**恢复成可继续状态**，但不自动发消息。零风险，但用户还是要自己一个个点开。
- **语义 B（自动续跑，白名单）**：启动后对清单里标记为"运行中"的会话逐个恢复并投递"继续"，**串行**、有并发上限与轮次预算。
- **语义 C（全部自动续跑）**：需求原话的字面版本。**不推荐**：多会话同时改文件、token 无上限、且"继续"可能重做那些"工具结果未知"的副作用操作。

平台的立场很明确地偏向 A：恢复后目标是**未授权**的（平台注释即"移除本进程内的续跑授权"，需要人类显式重新武装）。
⇒ **自动续跑 = 绕过平台设的人类阀门**，因此必须 opt-in + 限定范围，而不是默认全开。

### 4.2 关闭时还有会话在跑，怎么办？

- **拒绝关闭**（提示"N 个会话在跑，先停下"）：最安全，体验差。
- **等静默**（等空闲 + 超时）：体验好，但一个长回合可能等很久，且期间用户已经点了关闭。
- **立即中断并标记**：最快，会留下未闭合回合（读侧补"工具结果未知"），需要把"人为中断"记进清单以免下次被当成崩溃续跑。
- 另有硬约束：**审批无人应答时按失败关闭**。⇒ 在跑的会话若正等审批，等静默会一直等到超时。

### 4.3 "计划内关闭" vs "崩溃"必须可区分

否则每次断电/崩溃后重启都会触发"自动继续所有会话"——那正是最不该自动续跑的场合（状态未知、可能有半成品文件）。
清单里必须带一个**关闭原因**字段，启动接管半区按原因决定是否续跑。

## 5. 推荐形态（分三档，按风险递增）

**档一 · 优雅关闭 + 待续清单（低风险，建议先做）**
1. 客户端（纯人类入口）加"关闭 DSH"动作，位于侧边栏/替换槽位（不注册任何工具，**绝不进模型工具面**——与既有硬规则"宿主不得由 agent 自行重启"同源）。
2. 宿主侧顺序执行：快照活会话 → 落盘（当时的写法是先 flush；复验后降级为冗余保险）→
   写一份待续清单（会话 id、工作目录、当时状态、标题、关闭原因、时间戳）→ 广播"正在关闭"给客户端 → 让宿主退出。
   ⊖ （复验修正：退出这一步必须**投递到平台的处理者**；把信号"发给本进程"在 Windows 上是进程级强杀，平台的落盘与收尾都不会跑）
3. 页面转入"已关闭"遮罩（可选：一个"重新启动"按钮，形态退化回 restart-fab）。
4. 下次启动：读清单 → **只恢复、不续跑**，在界面上给一张"上次有 N 个会话在跑"的卡片，一键"继续"。

**档二 · 白名单自动续跑（中风险）**
在档一上加：只有被用户勾选过"允许自动续"的会话才自动恢复并投递"继续"；串行执行、并发=1、每会话预算上限、失败即停并通知。

**档三 · 全部自动续跑**：不推荐（理由见 4.1）。

**外部前提**：档一的"关闭"要真生效，必须先解决 §3 的看门狗冲突（落"计划内关闭"标记 + 看门狗识别；或关闭时禁用该计划任务）。
另外"下次启动"依赖用户自己启动 DSH —— 这一点插件无法保证，报告里应如实说明，不要承诺"关了还会自己回来"。

## 6. 验收口径（真要做的时候照这个验）

| 编号 | 判据 | 怎么验 |
|---|---|---|
| A1 | 关闭入口是**人类专属** | 全仓无对应的工具/命令注册；模型工具面列不出该入口 |
| A2 | 关闭前落盘真的发生了 | 关闭前后比对会话日志的**字节数与末事件序号**（未落盘的事件在强杀对照下会缺失——用"强杀 vs 优雅关闭"双跑做差分，两个变体都要能复现） |
| B1 | 清单内容正确 | 清单的会话 id 集合 == 关闭开始时的活会话快照；状态字段与会话列表同一口径 |
| B2 | 关闭原因可区分 | 人为关闭、重启、崩溃三条路径各跑一次，清单里的原因互不混淆 |
| C1 | 启动接管**默认不续跑** | 冷启动后观察：清单里的会话被恢复但没有新的用户消息进入日志 |
| C2 | 续跑受白名单约束 | 未勾选的会话在冷启动后始终处于空闲态 |
| D1 | 不会重复执行副作用 | 构造一个含"工具结果未知"的中断会话，验证续跑时模型能看到"结果未知"的合成结果文本（而不是当成成功） |

## 7. 风险清单（一句话版）

1. **关不掉**：看门狗/启动脚本自动重拉，用户以为关了其实又起来了（§3，当下即刻存在）。
2. **续跑 = 撤销人类阀门**：平台刻意让恢复后的目标处于未授权态（§4.1）。
3. **无人应答即卡死**：审批按失败关闭；离场模式只管提问不管审批（§4.2）。
4. **重复副作用**：中断回合的工具结果未知，模型"继续"时可能重做（§1.3）。
5. **多会话并发写盘**：串行化即可规避，别省这一步。
6. **自我指涉**：关闭按钮就在你正在用的这个宿主上——点下去当前会话（包括持有它的 agent）一起结束。
   这是设计意图，不是缺陷，但必须有确认与遮罩。

- 运行中宿主的插件源码基址是 **npx 缓存**，与全局安装路径**不是同一份**——做宿主半区改动时要确认改动落在真正被加载的那一份上。
