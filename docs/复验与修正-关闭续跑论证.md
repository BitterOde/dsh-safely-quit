# 复验与修正：《DSH 关闭续跑插件可行性论证》

日期：2026-10-04（平台实读复验）｜复验对象：同目录那份《「关闭 DSH 并在下次启动自动继续会话」插件 — 可行性论证》（研判存档的改写稿；原件为存档稿）
复验方式：对原文的**关键前提**逐条回读平台包源码（实读，非 grep 断言）；只读，未改任何插件代码。
原件：`<原文留档路径>`（17695B，SHA256 前缀 `82b11ce8`）。

> **摘要（2026-10-12 补充，先看这五行）**
> 1. 原文的**需求分解**（三段式）、**社区盘点**、**风险清单**成色高，可以直接用。
> 2. 原文有一条贯穿全文的地基性错误：认定"平台没有优雅关闭路径，终止信号即硬杀"。实测**不成立** —— 平台自带完整优雅关闭链路，且已包含落盘屏障（§1、§2）。
> 3. 但**平台有能力 ≠ 你发的信号一定到得了它**：Windows 实测把终止信号"发给本进程"是**进程级强杀**，平台的处理器不跑（§1.1）。
> 4. 所以插件关闭的最后一跳必须**投递到平台的处理者**：优先请平台自己的关停控制器接管，拿不到就在进程内派发关闭信号事件，两条都不接住才兜底自退。
> 5. 原文 §5 的 M1（关闭前手动落盘）由此从"必需"降级为"冗余保险"；插件真正要做的只剩三件：**意图清单、关闭入口与界面、与外部启动器的协议**。

## 1. 反证一：宿主本来就有终止信号处理器

真实存在的一份是**被实际加载的那份**（运行实例来自 npx 缓存，与全局安装路径不是同一份）：

```js
// 宿主启动引导段（profile-boot-*.js:223-236）
const shutdown = createProcessShutdown(async () => {
    await app.current?.fiber.dispose();      // 整棵框架树有序拆卸
});
const signalShutdown = new AbortController();
const interrupt = (code) => {
    signalShutdown.abort();
    shutdown.interrupt(code);
};
process.on("SIGTERM", () => { interrupt(0); });
process.on("SIGINT",  () => { interrupt(130); });
```

`createProcessShutdown`（同文件 `:11`、`:20-52`）的语义：

- `PROCESS_SHUTDOWN_TIMEOUT_MS = 5e3` —— **5 秒 grace**；
- `start(code, forceAfterDispose)`：先 `await dispose()`，完成后若 `forceAfterDispose` 则 `process.exit(code)`；**dispose 抛错或超时都走兜底强杀**；
- `interrupt` 走的就是 `forceAfterDispose = true` 那条（另一条只设退出码，让进程自然退出）。

⇒ **平台那套有序关闭是这样触发的：进程收到关闭信号事件 → 有序拆卸整棵树 → 落盘 → 退出；只有 5 秒内没拆完才会被强杀。**

原文"全量包 grep 零命中"与实际不符：同范围实测命中 19 处，其中宿主的 2 处就是上面这段。
（其余命中在子进程与 shell 桥接那几个包的信号族，与关闭语义无关——原文若只 grep 了某一层目录、或用了会误判编码的取词方式，容易漏掉这里。）

### 1.1 ⚠ 但"把信号发给本进程"不等于"信号事件到了监听者"（2026-10-12 实读）

这一条是复验之后**新补的硬事实**，也是本插件关闭路径曾经走错的根因：

| 关法 | 真子进程实测 | 平台的处理器跑了吗 |
|---|---|---|
| `process.kill(process.pid, 'SIGTERM')` | **进程级强杀**：`exit=1`、监听器**从未被回调**、300ms 后进程已不在 | **没有** ⇒ 拆卸、落盘、其它插件的拆卸收尾**全被静默跳过** |
| 请平台自己的关停控制器接管（本插件现用） | **285ms 自行退出**、日志显示"交棒：走关停控制器" | **跑了**（`fiber.dispose()` + 落盘） |
| 在进程内派发关闭信号事件（拿不到控制器时的退路） | 监听器被回调（对照读数） | **跑了** |

⇒ 结论写死：**"交棒"必须投递到平台的处理者**，不能把信号"发给进程"了事。
本插件因此改成三条路：请平台关停控制器接管 → 进程内派发关闭信号事件 → 都有上限兜底自退。

## 2. 反证二：持久化后端在自己的拆卸里落盘

`@deepseek-ai/dsh-session-persistence`（**基类**，不是 jsonl 子类）：

```js
// :1135-1141   dispose effect
let disposeError;
try {
    const errors = await settledErrors(
        [...this.live.keys()].map((session) => this.flush(session))
    );
    if (errors.length > 0) throw new AggregateError(errors, `${this.backend.name} dispose failed`);
} catch (error) { disposeError = error; }
// :1158-1164
ctx.on("session/flush",   (session) => this.flush(session));
ctx.on("session/disposed", (session) => { /* Start and observe one disposed session's final drain. */ });
// :1303
async flush(session)
// :335-346  SessionWriteBehind.flush()
/** Cancel the batching wait and durably drain through a quiescent point. */
```

配套的两条官方陈述与之互证：

- 会话持久化的 jsonl 实现 README（`:52`）：
  "…`session/flush` cancels the wait and drains current and pending batches. … **disposal drains every retained controller before teardown.**"
- 会话存储层的注释（`dsh-session/lib/index.js:1581-1582`）：
  "Persistence is intentionally not implemented here — persistence plugins subscribe to `session/event` and **flush on `session/flush` / dispose**."

⇒ 原文 §1.2 认定的"不落盘就会丢东西、而平台不做"——**平台做**，且是**等到写盘排空到静默点**才放行退出。
**前提是 §1.1 那条：关闭请求真的投递到了平台的处理者。**

**修正后的缺口清单**：关闭前的**落盘**由平台负责；插件真正需要做的只有
①**活跃会话意图清单**（谁在跑、跑到哪、为什么关）②关闭入口与客户端界面 ③（可选）与外部启动器的协议。
原文 §5 的 M1 第 2 步里"手动逐会话落盘"从"必需"降级为"冗余保险"
（保留也不亏：它能把落盘提前到用户可感知的时点，并在 5 秒预算耗尽被强杀时多一层兜底）。

### 2.1 这条"不丢事件"的验收口径（D1）跑到哪一步了

项目自己把这条写成了验收判据：**关闭前后比对会话日志的字节数与最后一条事件的序号**，
对照做法是"强杀 vs 本流程"双跑差分。2026-10-12 的真机读数：

- **机制层已达成**：本流程确实走了平台那趟（285ms 自行退出、拆卸与落盘真跑）；强杀那跑 `exit=1`、无拆卸。
- **会话日志这一维度：双跑没有差分**（两跑都是 18 事件、末序号 16，关停前后未变）。
  原因很实在：会话日志按事件即时落盘，关停那一刻没有"还在内存里的事件"可丢。
- **有差分的地方**：待续记录与"计划内关闭"标记只在"本流程"那跑出现 —— 证明的是**清单与标记在关停前确实已落盘**（用户可见契约），不是"平台落盘有没有跑"。
- **局限（如实写）**：隔离 home 没有凭据，没能构造出"关停瞬间确有未落盘事件"的场景 ⇒
  "不丢未落盘事件"这句话在本装置下**没有被证伪，也没拿到正面强化**。要它有判决力，得另配带凭据的隔离实例。
  这条随冻结清单交独立验证。

## 3. 架构修正：不要绕开关闭仪式，挂进去

原文的推理链是："插件活在宿主里 → 宿主一死插件也没了 → 关闭前的事必须插件抢在自杀之前做完（落盘 → 写清单 → 再杀）"。
链条的前半仍然对，**结论要改**：

- **旧**（原文）：插件自造一套关闭仪式，赶在结束进程之前把落盘与清单都做完。
- **新**（复验后）：宿主已有一套**有序、可等待、有 5 秒预算**的关闭仪式；插件应当**以拆卸 effect 的形式挂进它**，
  与持久化的落盘处在同一个**会被等到**的流程里，而不是在外围抢时序。

由此得到两条新的硬约束与一个待验问题：

1. **5 秒总预算**：拆卸阶段所有参与者共享 5 秒；插件在拆卸 effect 里的工作必须远小于此（写一个 JSON 文件是微秒级，安全）。
2. **清单必须在拆卸期仍可写**：插件私有目录下写 JSON 是普通文件写，不受沙箱影响；但**不能依赖宿主 HTTP 或客户端往返**（树正在拆）。
3. **待验（设计阶段第一件事）**：拆卸**顺序**。插件若注入 agents 面，它的拆卸 effect 与持久化的拆卸 effect 谁先？
   在插件自己的拆卸里枚举活会话是否还能拿到？——拿不到就必须改用更早的时点快照
   （例如"状态事件持续维护 + 关闭开始时的一次前置快照"）。

> 换句话说：原文第 17 行"最大的结构性事实"仍然成立，但它推导出的**实现位置**变了 ——
> 不是"插件在外面把活干完再杀宿主"，而是"插件在宿主的关闭流程里被调用"。
> （本项目最终的做法是前者与后者的结合：**关闭编排在树还活着时做完，最后一跳请平台接管**。）

## 4. 仍然成立的结论（复验为真，可直接采用）

- **社区先例三条全部属实**（插件 registry 缓存）：
  - `dsh-auto-continue`（repo `HsiangNianian/dsh-auto-continue`，npm `dsh-client-auto-continue`）；
  - `dsh-restart-fab`（repo `miisaka19800/dsh-restart-fab`）；
  - `dsh-shutdown-after-task`（repo `virggle/dsh-shutdown-after-task`）。
  ⇒ "用户的想法 ≈ restart-fab + auto-continue 的并集，真正新增的只有『关闭』与『多会话』"这个判断可用。
- **可抄实现路径在位**：一次性的重启助手脚本 ✓、常驻看门狗脚本 ✓。
- **运行实例来自 npx 缓存**（原文 §8 的关键提醒）已复核：当时宿主是普通 `node.exe`、监听回环端口、浏览器侧多条长连接；
  被加载的包在 npx 缓存路径下 —— 与全局安装路径**确非同一份**。
- **写盘批窗语义**（原文 §1.2）：批窗默认 200ms、落盘与拆卸绕过它 ✓。
- **启动脚本末尾有 `pause`** ✓（实读），结束 node 后那个黑窗不会自己消失这一条成立。

## 6. 由既有用户级硬约束推出的设计约束（自决，不进待裁定队列）

复验时核到两条既有用户级硬规则：

- 「**禁止 AI 自行重启或关闭 DSH**，以及执行任何会中断在飞 Agent 工作的操作；需要重启时交由用户手动执行」
- 「未经用户明确指示不得重启运行中的 `dsh web` 服务，需要重启时先询问」

由此直接推出三条，均属"能按既有已裁定口径推出"，**自行决定、不推回用户**：

1. **关闭入口必须人类专属**：不注册任何模型可见工具或命令。原文 §5 的方案一第 1 条已如此主张，此处补上规则出处 —— 它不只是设计偏好，是既有裁定。
2. **「关闭」行为不得在当前宿主上做真机验收**：在这儿点一次，会连同本会话与其在飞 agent 一起结束 —— 既直接违反上述规则，也毁掉验收现场。
   验收须在**隔离实例**上进行（出厂模板临时 profile + 链接装包 + 独立端口 + 无头进程；本项目已把这套做成可重复的真机装置）。
   已知坑：无凭据的隔离 home 起不了真回合，探针设计须绕开。
3. **宿主半区改动交用户重启生效**：挂载走 profile 的 bundle 通道或 dev 补丁层，改完请用户重启 DSH；不得自行重启。
   另注意链接装包会触发行程管理器的重整动作，可能波及同 profile 下其它插件 ⇒ 跑完须逐个复验关键链接依赖仍解析到各自真实路径。
