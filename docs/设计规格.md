## 1. 范围

**做**：

- 一个**人类专属**的「关闭 DSH」入口（不注册任何模型可见工具 / 命令）。
- 关闭动作：按 §2 的时序，让在跑的会话各自跑完**当前一步**后停止、并登记，全部停止后关闭宿主。
- 下次启动：读清单，**一键继续** —— 给一张「上次关闭时有 N 个会话在跑」的卡片，点下去**真的接着跑**
  （宿主把一条**插件来源**的续行消息投进那个会话并唤醒驱动：`agent.followup` + `sessions.flush`，
  只这一轮）；**不产生任何用户消息**（消息的 `source.kind` 是插件，界面把它画成"非人触发的本轮"）。
- 对外服务**关机拓展**（§2.3）：其它插件登记"关闭时要执行的动作"，本插件统一排序 / 限时 / 隔离失败地执行。

**不做**：

- **不自动续跑**（白名单式或全量式都不做）：是否继续由人在卡片上点；**接续只投一条消息、只跑这一轮**
  —— 不设任何"空闲就自己再开一轮"的机关（目标原语会那样做，见下）。
- **不替用户发消息**：接续那条消息的来源标成插件（`source.kind='safely-quit'`），不冒充用户输入；
  也不用平台的目标（goal）原语 —— 目标是一份持久目标，一武装就会无人值守地自动开下一轮，
  还会在会话里留下一个用户从没设过的目标。
- **不改系统配置**：计划任务 / 启动项 / 注册表一律不碰。

**落地状态**：三段全部实现。关闭编排在宿主半区，界面在客户端半区（**坞里一行** = 关闭 / 收尾态 / 立即停止；
**独立浮层卡片** = 启动半区的「一键继续」，不进按钮面板）。
平台原语两条：① 切换会话（把某个会话选成当前会话，客户端）；② 接续 agent loop（宿主：
`sessionController.resolveAgent` → `agent.followup(插件来源的消息)` → `sessions.flush`，
与平台自己的定时提醒（`dsh-schedule`）同一条路；不碰目标服务，不发用户消息）。
离线判据 **1022 条**（宿主 396 + 客户端 626，2026-10-18 实测）；真机装置（待续记录生死）33 条，见 §7。

### 1.1 启动半区的用户可见文案

| 位置 | 文案 |
|---|---|
| 卡片标题 | 上次关闭时有 N 个会话（M 个在跑）—— **N 恒等于卡片里的行数**，M 只数其中"关闭那一刻被打断"的；N = 0 ⇒ **不弹卡片**（见 §1.2） |
| 每行那颗键 | 「继续」——点它就是接着跑（把这一个会话的 agent loop 接回去） |
| 卡片底部那颗**总键** | 「一键继续」——一次把这张卡片里的会话都接上 |
| 接上了 | 已接上 |
| 那条会话本来就在跑 | 已经在跑 |
| 会话已被删 | 这个会话不在了 |
| 没接上（会话服务缺席 / 宿主拒绝 / 投稿失败） | 没接上，再点一次 |
| 总键点完的回执 | 已接上 N 个（，M 个本来就在跑）（，K 个没接上） |
| ~~整卡收起~~ | ~~不用了~~ —— **已删除**：关掉面板本身就是"不用了"，记录随之清空（§1.7） |
| 关闭半区的坞行（常态） | 关闭 DSH（**五档显示状态机见 §1.8**） |
| 关闭半区的坞行（已按下、等确认） | 再点一次确认关闭（**不带**说明文字） |
| 关闭半区的坞行（收尾中） | 立即停止（已等 S 秒）—— **一段文字**；"还有几个在跑"由右侧角标给 |
| 关闭半区的坞行（宿主已退） | DSH 已关闭（"可以关掉这个页面了"住悬停说明） |
| 关闭没成功 | 重试（失败原因住悬停说明） |

定稿口径：① 键名只说它干的事（**接着跑，像没中断过一样**），**不承诺替你发消息**；
② ⚠ **没有「打开」这一档**（用户明确否掉"只切会话、什么都不跑"那种空闲档）；
③ ⚠ **范围 = 被这次关闭打断的 agent loop**（设计口径：「我们只继续因为关闭中断的 agent loop」）——
**只有"关闭那一刻在跑的"进清单**（逐条口径与事故背景见 §4）：
· 界面**开着但当时空闲**的会话**不进清单、也不继续**：它没有被打断的 loop；开着这件事只记进
  `scope` 作诊断（回答"我开着的那个为什么没列"）；
· **子代理（subagent / AgentTeams 成员）折算成它所属的顶层会话**，不单列（子代理会话平台拒绝独立
  resume、跑完还会被回收，列出来就是死链）；
· **本次运行里翻到过、关闭时并没在跑的会话一律不进清单**；
标题的条数**恒等于行数**（新记录每一行都是被打断的 ⇒「上次关闭时有 N 个会话在跑」；读旧记录时才出现
「N 个会话（M 个在跑）」的混合档 —— 曾出现"标题 2 个在跑、卡片 23 行"，账必须对得上）；
④ 不出现会话 / 恢复 / 目标这类技术词。

**接续＝投一条消息、跑这一轮**（不是"给会话设一个目标"）：

| 宿主看到的状态 | 动作 | 依据 |
|---|---|---|
| 会话空闲（冷会话先被恢复出来） | 投一条**插件来源**的续行消息并唤醒驱动 | 「继续」在设计原文里的定义就是"投一条下一轮消息并唤醒驱动"（可行性论证 §1.1） |
| 会话已经在跑 | 什么都不投，回「已经在跑」 | 再投一条会让同一段活做两遍 |
| 会话已经不在（`session/not-found`） | 回「这个会话不在了」 | 不拿别的会话顶替 |
| 会话服务缺席 / 宿主拒绝 | 回「没接上」 | 如实报，不静默换一条路 |

⚠ **只跑这一轮**：投递之后没有任何"空闲就再开一轮"的机关 —— 模型跑完这一轮就停，下一步仍由人决定。
⚠ **不碰目标（goal）**：目标一武装就会在 agent 空闲时自己开下一轮（默认上限 256 轮），那是无人值守的
自动续跑；被关闭打断的会话也根本没有目标，建一份等于替用户凭空造一个任务。
⚠ 清单之外的会话一律不碰（客户端只送清单里的 id，宿主再挡一道）。
续行消息的正文**只有一档**：「上次关闭 DSH 打断了这个会话正在进行的那一步。接着把它做完；
如果那一步其实已经完成，就按你原来的计划继续。」

**按钮不得相互嵌套（项目规则，硬约束）**：GUIFrame 渲染坞里每个条目时**已经套了一层**按钮
⇒ 我们的行**只渲染一个 `<div>`（0 个 `<button>`）**：
- 「关闭 DSH」与「立即停止」因此是**同一行在不同阶段的键**（不是两个按钮，也不是一个套一个）；
- 行内挂原生 click，并判定"点的是不是本行"，键鼠 / 回车 / 空格同一条通路；
- 机检：客户端判据里"本行按钮数 === 0"，且把行改回按钮、或注入嵌套按钮都会**变红**。

**提示只出现一次**：以前是"点过键或点「不用了」⇒ 把清单的时间戳写进浏览器本地键"。
那条路有个洞：浏览器换了 / 本地存储被清 / 用户是点页面把它关掉的，标记就不作数，于是**下次开机又弹一遍旧记录**——
而"下一次 DSH 根本不是用插件关的"，那份记录其实早就过时了（用户报的 bug）。
现在这件事由**宿主盘上的记录自己**管：卡片站稳 ⇒ 界面认领；用户关掉面板 ⇒ 界面清空。判据与全生命周期见 §1.7。

### 1.2 卡片长在哪

坞入口的**动作行**要点开面板才看得见（角标也一样）⇒ 只放坞里等于"没有按钮"。落地为：

| 路径 | 形态 | 何时出现 |
|---|---|---|
| **浮层卡片（唯一去处）** | GUIFrame 的公开浮层面（`family:'panel'`） | **清单里有会话**且没认领过 ⇒ 开机就弹；清单为空（**这一刻没有任何 agent loop 被打断**）⇒ 不弹 |
| 坞入口 | 只有那一行动作本身（关闭 / 收尾 / 立即停止）与其角标；**卡片不放进来**，也**没有"打开面板"兜底** | 一直在（不需要打开面板就能看到角标） |

**弹不出来要如实说，不换形态**：浮层落地后立刻机检"层标记在不在 DOM、与视口相不相交"；不满足 ⇒
记"没有继续路径" + 浮层报错，并自报给宿主，**不悄悄换成别的东西** ——
**这条是被两轮"接口返回句柄、界面没卡片"教出来的**：调用成功 ≠ 界面出现，必须有落点机检。

### 1.3 收尾态归谁管

**状态机住在模块里，不住在组件里**。GUIFrame 每次打开坞面板都**现造**内容节点
⇒ 面板一关组件即卸载；状态若住在组件里，收尾中关掉面板再打开就回到「关闭 DSH」，
而且组件里的轮询会跟着一起死（界面再也追不到"已关闭"）。

落地：模块级 store 持有收尾状态、宿主读数、失败原因、开始时刻与已等毫秒数，**轮询与确认态的超时也归它**；
组件只订阅 + 渲染。另外每次挂载都向宿主对齐一次 ⇒ 收尾中**刷新页面**、以及客户端半区被**热换模块**之后，
界面都能接着显示收尾态。

### 1.4 坞内那一行的外观契约

**行盒归坞，插件只做内容。** 坞给每个入口条目包一层按钮，它的取值是侧栏行样式的**逐值照抄**：
内边距 / 行距 / 最小高度 / 字号 / 行高 / 圆角 / 悬停底色整行一个面。
**注册方的控件若自带其中任何一项**，内容就会相对邻居多缩进一截、整行也被顶高一截 —— 这不是"风格差异"，是**不在一条竖线上**。

真机读数（装置：坞内几何对齐那台，见 §7；对照组 = 同坞里另一个已对齐的插件）：

| 量 | 改前（本插件） | 邻居（已对齐的那家） | 改后（本插件） |
|---|---|---|---|
| 图标左内缩 | 18px | 8px | **8px** |
| 行高 | 46px | 36px | **36px** |
| 文字字号 / 盒高 | 13px / 13px | 14px / 22px | **14px / 22px** |
| 文字色 | 比邻居重一档的主题色 | 次级标签色 | **跟随行（inherit）** |

落地三条（都在客户端半区的样式表里）：
1. 我们的按钮类**不带**内边距 / 固定高度 / 圆角 / 自画悬停与位移；尺寸只由行给，颜色跟随行色；阶段色只改颜色，不动盒子。
2. 竖排包装层**不许给高度**（高度只能来自内容），并给右侧角标让位（角标是自动外边距的兄弟节点，包装层不设收缩下限会把它挤出可视区）。
3. 契约由客户端判据的 7 条样式判据锁住（改回自带外壳 ⇒ 变红；已做两发定向变异验证）。

### 1.5 坞角标 = 循环中会话数

设计口径：「把它改成"循环中会话数"，显示出：**如果关闭，需要暂停的总会话数**。」
（此前它数的是"上次关闭时的待续清单"，属**开机快照**，与"现在关会怎样"无关。）

| | 旧口径（作废） | 现口径 |
|---|---|---|
| 数什么 | 上次关闭时登记下来的会话（优先"那一刻在跑的"，没有就数总数） | **现在**会话列表里在跑的行数 |
| 什么时候变 | 只在开机注册那一刻算一次 | **实时**：订阅会话列表，平台经状态帧推着走 |
| 0 个时 | — | **不画角标**（坞的面板行会把 0 真画出来，所以必须给它"空"） |
| 与"看没看过"的关系 | 看过就不再显示 | **无关**：它是当前状态读数 |
| 悬停说明 | 通用一句 | 有在跑 ⇒「现在有 N 个会话在循环中：关闭会让它们各自跑完当前一步再停」；0 个 ⇒「现在没有会话在循环中：关闭会直接收尾」 |

**为什么这个数就等于"关闭要暂停几个"**：宿主收尾时正是把"状态=在跑"的会话逐个放到 step 边界停下，空闲的本来就不等。

**两条推送通道**（都推同一个值，幂等）：① 主通道 = 坞的切片面角标接口（面板关着也更新侧栏那一行；
⚠ 该接口是**三参**，第一个恒为调用方上下文，按两参调会静默返回 false）；② 退路 = 组件 props 给的"每行能力面"。
读数还进了自报：角标值 / 当前在跑数 / 有没有拿到会话列表三项 ——"有没有拿到列表"为假就说明角标不实时。

### 1.6 开机卡片的「存活契约」

用户报的现象：「我看到插件的『继续』面板了，但是，那只有一瞬间，面板很快被关闭了」。
真机上量到的时间线：卡片约 1206ms 出现 → 1824ms 消失，而浮层根**全程在**。

三条成因，逐条定契约（均已落地 + 离线判据 + 真机复验）：

| # | 成因 | 旧行为 | 现行为 |
|---|---|---|---|
| ① | 探针量的是**层包裹节点**，而它不生成盒子（`display: contents`）⇒ 量出来恒 0×0 | 判"没弹出来" ⇒ **把用户看得见的卡片当场关掉** | 层自身没盒子就**下沉子树**量（并集）；探针**只用来记账，绝不据此关卡片** |
| ② | 平台服务晚到：浮层先装**降级件**、就绪后拆卸 + 补装，而拆卸会**清空层栈** ⇒ 补装窗口前开的记录被清掉 | 只开一次 ⇒ 层永远不出现（冷启动） | 「开 → 核验层在不在 DOM → 需要就重开」跨过补装窗口（实测约 7.3s；外壳完整时第一次就成） |
| ③ | 装配期层栈被清（同 ②，但发生在卡片**已经渲染出来之后**） | 卡片"闪一下就没了" | **看护**：确认在场后 8s 内，只要"**用户没动过**"却消失就重开（上限 5 次）；用户一有动作立刻收手 |

**"用户关的"与"平台清的"怎么分**：两者在 DOM 上长得一模一样（层没了）。分界线是**用户交互**——
点外 / Esc / 面板 × 这几条路都必然先有一次用户交互，而平台清栈不会 ⇒ 用户动过就再也不重开。
⚠ **面板 × 是 React 的 onClick**：摘层发生在**点击事件之后的 React 提交里**，交互当场那一看层还在 ⇒
只看"当场"会把用户刚关掉的卡片判成"与卡片无关"再打开（真机读数：用户点了 4 次 ×，卡片 4 次自己回来）。
所以交互之后要**再复核一次**（`INTERACTION_REVIEW_MS` = 120ms，见 §1.8 的守望纪律），层没了就改判成"用户关的"。
另：**重开之后要有宽限拍**（`REOPEN_GRACE_TICKS` = 3 拍）—— 层不会立刻出现，不宽限就是每拍重开一次、
额度瞬间烧光（真机 `reopen` 连发三次、中间一次 `reappeared` 都没有）。

**卡片长什么样、够不够得着**：实测一份 11 个会话的清单 ⇒ 卡片实体高约 365px，而浮层只给了 300px；
内容区是滚动的 ⇒ **卡底那颗「一键继续」得滚动才够得着**。处置：开出来之后量内容区还差多少并按它补齐，
最多两轮（滚动条的出现/消失会改变内容宽度、行内文字随之换行，所以一轮补不干净）；拿不到内容区锚点时退回估算。

**仍然成立的一条**（未改）：卡片是 `panel` 族 ⇒ **Esc / 点外即走**。若希望"必须点「不用了」才走"，
公开面已有开关；这条是产品口径选择，已进待裁定队列。

### 1.7 待续记录的生死契约

需求原话：「如果用户关闭了面板，那么继续会话的记录自动清空；**只有用本插件的按钮退出时，记录才会写入**；
**如果记录中没有内容，打开 DSH 时，面板就不显示**。这样能解决一个 bug：如果不是通过本插件关闭了 DSH，
目前插件面板中还会有过时的记录。」

**总原则：记录存在 ⟺ 有一份「还没交给人」的待续清单。**

| # | 规则 | 落点 | 判据（离线） |
|---|---|---|---|
| ① | **只有本插件的按钮关闭会写** | 关闭编排的两处落盘（进等待时先落一次、交棒前落最终版） | 其它任何关闭方式（关终端 / Ctrl+C / 断电 / 平台自己的优雅关闭）都不写；演练走另一条分支（写记录但不关宿主） |
| ② | **交给过界面就作废** | 卡片**站稳**（连续两拍都在 DOM）⇒ 界面认领 ⇒ 记录写"交付时间 + 本次运行标识"；**下一次开机**（新运行标识）读到"不是自己"⇒ 判定过期、**当场回收** | ★ 这就是用户报的 bug 的判据；同一次运行里刷新页面仍会显示 |
| ③ | **用户关掉面板就清空** | 卡片的**每一条**关闭路径（点外 / Esc / 面板 × / 点过键之后关掉）都会让守望发现"层没了 + 刚有用户交互" ⇒ 清空 ⇒ 删文件。面板 × 是 React onClick（点击之后才摘层）⇒ 交互后**延迟复核**一次再判（见 §1.6） | 「不用了」那颗键因此被删掉；时间戳对不上时**拒绝删除**（不许误删刚存好的那份） |
| ④ | **空记录不显示** | 三种"没内容"在开机读取时直接回收：关闭原因不是"用户请求"（例如演练）、**记录里的会话数 = 0**、JSON 读不出来 | 只有"一个会话都没有"才收；记录里有会话（哪怕个都没在跑）就交给界面列出来 |
| ⑤ | **失败的那趟不算关过机** | 关闭编排中途失败时，这一趟写下的记录被标成"关闭失败" | 开机读数按"非用户请求"当场回收 —— 不给用户留一份骗人的待续提示 |

**为什么"认领"要等站稳（连续两拍）而不是一进 DOM 就发**：本项目出过一次"卡片只闪一下就没了"的事故（§1.6）。
闪一下不算交付，认领错了这份记录**再也不会被提示**（下次开机读到"已交付"就回收）。
反过来，"一次都没弹出来"（浮层宿主没挂）⇒ 记录仍是"没交出去过"，下次开机会再试一次 —— 不是白白作废。

**客户端这一半的守望循环**（1 秒一拍）：

| 阶段 | 触发 | 动作 |
|---|---|---|
| 补弹 | 一次都没进过 DOM | 1 秒一次、最长 60 秒继续开（跨平台服务补装窗口），**不看用户交互** |
| 认领 | 层连续在场两拍 | 认领（失败下一拍重试，**最多 5 次** —— 宿主还没这版接口时不许每秒刷；诊断账上限 60 条） |
| 守望 | 认领之后一直盯着 | 层没了 + 刚有用户交互（2.5 秒窗口）⇒ 清空记录、收手；层没了 + 没人动过 ⇒ 补开（额度 5 次），用完收手（记录留着不动） |

**这条契约同时替掉了两样旧东西**：浏览器本地存储里的"看过了"标记（整条路径删除），以及卡片上的「不用了」键。
"提示只出现一次"不再依赖浏览器，而是宿主盘上的一份事实。
**存查面**（排障用，三条都只读）：开机读数（**会回收**）、诊断读数（**不回收**，记录原样 + 本次是否已认领）、客户端自报里的守望账。

### 1.8 坞入口那颗键的显示状态机

**真源 = 客户端半区里的状态表（五档显示定义）+ 转移表**：视图构造函数只做"查表 + 填动态值"，
组件只查表渲染 —— **组件里不许再出现"如果阶段等于…"这种分叉**（换阶段只改表）。

**键上只有一段文字**：每档一个标签函数，键上就是**一个**文字节点（树里恒为 [图标, 那段文字] 两个节点）；
必要补充（"已等多久"）**直接拼进那段文字**，其余补充（失败原因、"可以关掉页面了"）一律进悬停说明。
"还有几个会话在跑"由**右侧角标**（§1.5）实时给出，不在键上重复。

| 状态 | 键上那一段文字 | 悬停说明 | 颜色档 | 可点 | 点击号令 | 号令做什么 |
|---|---|---|---|---|---|---|
| `idle` | 关闭 DSH | 读数档（见下） | 常态 | 是 | `begin` | 进确认态 |
| `confirming` | 再点一次确认关闭 | 读数档 | 警示色 | 是 | `confirm` | 发起真关闭，先进收尾态 |
| `closing` | **`立即停止（已等 S 秒）`**（拼成一个字符串） | 固定：`不再等待：立刻停掉仍在跑的会话` | 警示色 | 是 | `force` | 请宿主停止剩余会话（只发一次；真实进展靠 1 秒轮询） |
| `closed` | DSH 已关闭 | `可以关掉这个页面了` | 完成档（降低不透明度） | **否** | `none` | 点了不做事 |
| `failed` | 重试 | `关闭没成功：<宿主给的原因>` | 错误色 | 是 | `retry` | 解除失败态回 `idle`（**不是**重发关闭请求） |

> 未知阶段一律退到常态档（界面绝不出现空白键）。
> 读数档（悬停说明）：有会话在跑 ⇒ `现在有 N 个会话在循环中：关闭会让它们各自跑完当前一步再停`；
> 没有 ⇒ `现在没有会话在循环中：关闭会直接收尾`；读数缺席 ⇒ `在跑的会话跑完当前一步后停止，全部停稳后关闭`。

**转移表**（状态机每次换挡拿它对自己）：

| 边 | 触发 |
|---|---|
| 常态 → 确认态 | 点第一下 |
| 常态 → 收尾态 | 挂载/刷新时读到宿主正在收尾 |
| 确认态 → 常态 | 5 秒没确认（超时自己退回） |
| 确认态 → 收尾态 | 点第二下（先转态，再发关闭请求） |
| 收尾态 → 失败态 | 关闭请求被拒或网络失败 |
| 收尾态 → 已完成态 | 轮询连续失败 3 次（宿主真的退了），或挂载时发现宿主重启过 |
| 已完成态 → 收尾态 | 宿主又进了收尾（罕见） |
| 失败态 → 常态 | 点「重试」 |
| 失败态 → 收尾态 | 挂载时读到宿主正在收尾 |

**对账纪律**：换挡时转移表说这条边没声明过 ⇒ 控制台 + 调试面**留痕但不拦**
（界面优先：关闭流程不可逆，绝不能因为"账目不对"把人卡在收尾态）。

**判据**：五档齐全、每档字段齐全、**每档都没有"附加说明"通路**、转移表键集与状态表一一对应、
每档渲染视图逐项断言、**真跑一遍状态机且逐跳与转移表对账**、渲染树与机器同源（颜色 / 悬停 / 可点锚点 / 那段文字 / **节点数恒为 2**）。

> 宿主侧还有一个**毫秒级的过渡态**（失败之后重新受理的那一瞬间）：它同步地紧接着就被"等待中"覆盖，
> 客户端按"收尾中"处理即可，**对外仍是五档**。事实与判据见 §2.4。

## 2. 关闭时序

用户点「关闭 DSH」后**不是立刻杀掉自己**，而是进入一个可能持续较久的「收尾」状态：

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 置内部状态为"收尾中"，向客户端广播 | 界面转为收尾态，**不再是普通界面** |
| 2 | **快照**被这次关闭打断的 agent loop（= 在跑的） | 记下谁在跑（状态、id、所属会话；范围见 §4）。**子代理折算成它所属的顶层会话**。开着但没在跑的不进快照 |
| 3 | 对每个在跑的 agent 下"一步后停"指令 | **含子代理**：pre-step 按 agent id 生效，子代理一样停在 step 边界（否则会被 SIGTERM 半路带走）。见 §3 的机制 |
| 4 | 每个会话停稳即**登记** | 写入清单：会话 id、工作目录、标题、关闭前状态、停止时刻、停止方式 |
| 5 | 全部停稳 | 判据：逐个等到静默，或收到它的终止事件 |
| **5.5** | **关机拓展**：跑其它插件登记的动作（§2.3） | 树还活着、会话已停在安全边界；失败/超时只记账不阻塞（**演练不走这一步**） |
| 6 | 落清单 + 落"计划内关闭"标记（§5），然后**交棒给平台退出** | 此时无在飞工作，收尾余量充足 |
| 7 | 平台收尾：**有序拆卸整棵树 + 持久化落盘**，然后退出 | 由第 6 步的请求触发；**前提是请求真的到达平台的处理者**（见 §2.4） |

**关键点**：第 3–5 步发生在**树还活着**的时候，所以插件在此时仍能枚举会话，不存在"拆树时拿不到列表"的问题。

### 2.1 已空闲的情形
快照里没有在跑的会话 ⇒ 跳过 3–4，直接 5→6→7，用户感知为"点一下就关了"。
快照**空**（界面没开会话、也没有在跑的）⇒ 清单为空，开机按"空记录"当场回收（§1.7 ④），不弹卡片。

### 2.2 卡住的兜底
若某个会话长时间过不完当前一步（典型：它正卡在工具审批上，而审批在无人应答时按失败关闭），收尾会一直等下去。
**处置：不设自动强杀**（自动强杀＝擅自中断在飞 agent 工作，违反既有硬约束），而是
① 界面持续显示"已等多少秒"；② 那一行的键就地变成**「立即停止」**（同一行的键，行内不再套按钮，见 §1.1 的嵌套规则），
由用户显式点，点了才对剩余会话发取消。

### 2.3 关机拓展（对外服务 `safelyQuit`）

需求原话：「给外部提供关机拓展功能的服务 —— 我现在有其它自研插件，也有关闭 DSH 时执行某些命令的需求，
我希望通过这个服务，把功能集成到一处。」

**为什么值得单开一个服务**（同类与生态位调研）：

| 事实 | 证据 |
|---|---|
| 平台**没有**任何"登记关闭动作"的服务 | 平台对外提供面全量 11 处里只有"发起退出"与"启动就绪"与生命周期有关；`onShutdown` / `shutdownHook` / `registerShutdown` 等关键词 0 命中 |
| 框架的"拆卸事件"**在本平台不是事件**（写了不报错、永不触发） | 事件表只有内部事件；全平台没有对应的派发点。已有三处踩坑（清定时器成了死代码、降级分支永不执行、守卫来不及收） |
| 生态里**只有本插件在编排关闭**，别人都是"自扫门前雪" | 有真子进程要收尸的、有关闭时要还原系统状态但**没等到收尾**的（5 秒 grace 里可能被掐断） |
| 真实清理面只有"随组件撤下的析构器"，异步析构会被等到 | 框架并行跑各 fiber 的析构器（抛错被吞成日志），加上平台 5 秒总预算 |

**服务形状**（对外提供 `safelyQuit`；模块级依赖声明一律留空 —— 缺服务只该让消费者自己降级）：

登记沿用平台既有的"可撤销登记"惯例：登记一次，随登记方一起撤下；同一个登记名再登记一次＝替换（热重载友好）。
消费方的写法见包级 README 的对外服务一节 —— 规格这边只定服务面，不抄一份调用样例。

| 服务成员 | 作用 |
|---|---|
| `onShutdown(action, options)` | 登记一条动作；**返回摘除器**（幂等，挂到调用方 effect 上即随它卸载）。同 id 再登记＝替换（热重载友好） |
| `off(id)` | 按 id 摘掉 |
| `list()` | 只读：注册表（含每条的状态 / 耗时 / 失败原因 / 命令输出尾巴） |
| `lastRun()` | 只读：最近一趟执行的总账 |
| `budgets()` | 只读：三档预算（消费者据此判断自己的超时设得合不合理） |
| `runNow(options)` | 手动跑一趟（排障用：确认自己登记的钩子真能跑，不必真去关一次 DSH） |

**执行时机**（§2 时序里的**第 5.5 步**，在"全停"之后、"落清单 + 交棒"之前）：

| 入口 | 触发 | 预算（可配置覆盖） | 说明 |
|---|---|---|---|
| 主动关闭 | 用户点「关闭 DSH」且会话已全停 | 总预算 30000ms；单条缺省 5000ms | 此刻会话都停在安全边界、整棵树还活着 —— 跑外部动作最干净的时刻 |
| 兜底那趟 | 宿主**被动**关闭（Ctrl+C / 外部信号 / 控制台关闭） | 总预算 2500ms | 借平台关闭流程的 5 秒 grace 跑掉**还没跑过**的那些；热重载/卸载**不跑**（只有信号标记放行） |

**四条硬约定**：① 一条动作在**一次进程生命周期里至多执行一次**（两条入口共用同一份账）；
② 失败只记在它自己头上（抛错 / 超时 / 非 0 退出码），后面的照跑，整个阶段绝不抛穿调用方；
③ 排序只由声明顺序决定，不做依赖编排；④ **不提供"关闭 DSH"的触发口** —— 人类专属入口不变。

**可观测**：状态读数多一个关机拓展字段（阶段 / 总数 / 已完成 / 失败 / 正在跑 / 逐条明细），
客户端据此把收尾提示写成「正在执行关机拓展（1/3，已等 X 秒）」；每条动作开始/结束/失败各写一行 stderr。

### 2.4 最后一跳：交棒给平台（2026-10-12 定稿）

**现象（真机实测）**：把关闭信号"发给本进程"在 Windows 上是**进程级强杀**：
真子进程 `exit=1`、监听器**从未被回调**、300ms 后进程已不在。⇒ 平台的拆卸、持久化落盘、
其它插件挂在拆卸上的收尾**全被静默跳过**，所谓"5 秒 grace"在这条路上根本不适用。

**根因**：把"信号发给了进程"当成了"信号事件到了监听者"。进程级强杀不经过事件派发。

**做法（三条路，按优先级）**：

| 顺序 | 路径 | 读数 |
|---|---|---|
| ① | 请平台自己的**关停控制器**接管 | 真机实测：日志「交棒：走关停控制器」、实例 **285ms 自行退出**、兜底 10 秒未被用到 ⇒ 平台的拆卸 + 落盘真的跑了 |
| ② | 拿不到控制器 ⇒ **在进程内派发关闭信号事件** | 监听器被回调（对照读数），平台那条路照样走 |
| ③ | 两条都不接住 ⇒ **有上限兜底自退** | 1.5 秒（没有任何接手方时快退）/ 10 秒（接手了但迟迟不退）；兜底定时器一律 unref，不拖住正常退出 |

**不许再出现"把终止信号发给本进程"这种交棒**：判据里有一条"这条路径必须 0 次"的读数。
**失败之后仍可再关一次**：收尾失败的那一档不算"名额用完"，用户点「重试」要能重新受理一次真关闭
（否则这个进程里用插件关 DSH 的入口就永久失效）。

**这条的验收口径（不丢未落盘事件）跑到哪一步了**（2026-10-12 真机双跑差分）：

- **机制层：已达成**。本流程确实走平台那趟（285ms 自行退出、拆卸与落盘真跑）；强杀那跑 `exit=1`、无拆卸。
- **会话日志维度：双跑 0 差分**（两跑都是 18 事件、末序号 16，关停前后未变）——
  会话日志按事件即时落盘，关停那一刻没有"还在内存里的事件"可丢。
- **有差分的地方**：待续记录与"计划内关闭"标记只在"本流程"那跑出现 ⇒ 证明的是"清单与标记在关停前确实已落盘"（用户可见契约）。
- **局限（如实写）**：隔离 home 没有凭据，没能构造出"关停瞬间确有未落盘事件"的场景 ⇒
  "不丢未落盘事件"这句话在此装置下**没有被证伪，也没拿到正面强化**。要它有判决力，得另配带凭据的隔离实例。

## 3. 「一步后停」的机制

平台事实：

- 会话注册表返回**裸会话对象**；带"消费者能力"的句柄才能拆卸它 ——
  平台明说"持有裸注册表条目的观察者无权拆掉这个对象" ⇒ **插件无权拆卸别人的会话**。
- 裸对象上可用：取消当前驱动、等静默、读状态 / id / 所属会话。
- **"step 之前的决策"是协作式瀑布**：payload 带该 agent、已被独占认领的待处理消息、回合与步号、信号；
  决策可以是"拒绝进入"或"带消息进入"。

⇒ **"这一步做完就停" = 在 step 之前的决策点，对已列入收尾集合的 agent 返回「拒绝进入」**：
当前 step 正常跑完 → 下一个 step 被拒 → 驱动无新工作而收敛。**不会停在工具执行中间**，因此不会产生
"工具结果未知、续跑可能重做"那类歧义（复验文档里未覆盖的一项，在此被绕开）。

注意事项：
- 被拒的那一批消息，平台**已从收件箱认领移除且不会保留** ⇒ 收尾时要把这批消息**登记进清单**（记"有 N 条输入未执行"），不能让用户以为它跑过了。
- "拒绝"只作用于"下一次 step"。若 agent 已空闲，它本就不会再进 step ⇒ 无需处理。
- "卡住的会话"仍按 §2.2：只等待，等人点「立即停止」才取消。

```jsonc
  "hostPid": 10744,
  "deliveredAt": null,               // 界面把卡片显示到屏幕上之后才写
  "deliveredBy": null,               // 认领它的那次运行的标识；下一次开机读到"不是自己"⇒ 判定过期并回收
  "scope": {                         // 这份清单是"按什么范围"记的（只作诊断；开机渲染不读它）
    "open": 0,                       // 客户端上报"界面开着"的会话数（null = 没上报）
    "source": "mainView",            // 那份读数怎么来的：mainView | selection-store | none（null = 没上报）
    "running": 0,                    // 关闭那一刻在跑的会话数
    "recorded": 0                    // 最终记进清单的会话数
  },
  "sessions": [
    {
      "sessionId": "session-…",
      "cwd": "D:\\work\\proj-a",
      "title": "…",
      "statusAtClose": "running",     // 关闭开始那一刻的状态
      "stop": { "kind": "step-boundary", "at": "…", "step": 5 }, // step-boundary | delegated | already-idle（§4 后注）
      "droppedInputs": 0              // 被"拒绝进入"丢弃、未执行的输入条数（§3 注意事项）
    }
  ]
}
```

关闭原因三分：**只有"用户请求"才提示续跑**；没有标记文件（崩溃/断电）时不提示，避免无人看管时自动接管；
"关闭失败"那一档也不提示（§1.7 规则 ⑤）。

**清单里的会话是哪些**（本义 = "上次关闭时的会话"）：**「关闭那一刻界面上开着的」∪「关闭那一刻在跑的」**。

| 来源 | 谁给 | 为什么记 |
|---|---|---|
| **在跑**的会话 | 宿主快照（`status === 'running'`） | 它就是被 step 边界打断的那批 —— 清单只收这一档 |
| 子代理（subagent / 成员会话）在跑 | 宿主按 `isOwnedBy` 上溯到**顶层会话**再记（`stop.kind:"delegated"`） | 子代理会话平台拒绝独立 resume（`ApiSessionSubagentOwnership`）、跑完还会被回收 ⇒ 记它就是一行死链 |
| 界面**开着但空闲**的 | 客户端随 `POST /close` 上报（`openSessionIds`/`openSource`）→ **只进 `scope`，不进清单** | 它没有被打断的 loop，"继续"它等于凭空造一个任务；留痕只用于回答"我开着的那个为什么没列" |
| **其余**活着的会话 | —— | **不记**：它们只是"本次运行里被打开过" |

⚠ **这条范围是两轮事故收紧的**：① 原先拿"活着的 agent"（注册表顶层会话）当范围 ⇒ 那个集合是
**本次运行里被打开过的全部**（切走不会摘除），用户关闭那一刻界面一个会话都没开，卡片却列了 16 行
（跨 7 个工作区、最早两天前建的）；② 一度把"界面开着的空闲会话"也收进来 ⇒ 用户当场纠正：
「我们只继续因为关闭中断的 agent loop」。
**停止方式**（`stop.kind`）两档：`step-boundary`（它自己在跑）/ `delegated`（它空闲，但名下的子代理在跑）。
`already-idle` 只可能出现在旧记录里（兼容读取，不会被当成"被打断"）。

**记录的四条写/删通路**（都在宿主侧，客户端只按时间戳对准）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | 开机读数 | **会回收**：能提示就返回记录，不能提示的四类（坏/非计划内/空/过时）当场回收并在回执里说明原因 |
| GET | 诊断读数 | **不回收**：记录原样 + 是否被打断 + 本次是否已认领 |
| POST | 认领 | 时间戳对不上就拒绝 |
| POST | 清空 | 用户关掉面板时调；时间戳对不上就拒绝（防误删刚存好的那份） |

## 7. 验收口径

| 编号 | 判据 | 怎么验 |
|---|---|---|
| A1 | 关闭入口是**人类专属** | 全仓无对应的工具/命令注册；模型工具面列不出该项 |
| A2 | 关闭动作**不打断在飞的 step** | 构造"会话正在跑第 5 步"的场景，触发关闭 ⇒ 第 5 步的工具调用**有完整结果落盘**，第 6 步不存在 |
| A3 | 卡住时不擅自强杀 | 构造"会话卡在等审批"的场景 ⇒ 收尾保持等待，**不**自行取消；只有用户点「立即停止」才取消 |
| B1 | 登记正确 | 清单的会话 id 集合 ==「关闭开始时**在跑**的 agent 所属的顶层会话」（§4）；停止方式 / 步号 / 时刻与实际相符 |
| B2 | 关闭原因可区分 | 人为关闭、重启、崩溃三条路径各跑一次，原因互不混淆 |
| C1 | 启动**不替用户说话** | 冷启动后观察：清单里的会话被接着跑，但那一轮由**插件来源**的消息唤醒（`source.kind='safely-quit'`，界面画成"非人触发的本轮"），**没有任何用户发的消息** |
| C2 | 「一键继续」**真的接着跑** | 点行内键 / 总键 ⇒ 该会话成为当前会话**且**收到了那条续行消息（`/state` 的 `lastContinue` 有逐会话回执）；**只跑这一轮**（不武装任何自动续跑）；全仓无"冒充用户发消息"的调用（离线判据机检） |
| C3 | **记录的生死**（§1.7） | ① 卡片站稳 ⇒ 盘上的记录被认领；② 用户关掉面板（Esc / 点外 / 面板 × 任一）⇒ 记录**文件消失**，刷新页面不再弹；③ **不是用插件关的 DSH** ⇒ 下次开机**不显示**那张卡片，且过时记录被回收；④ 关闭失败那趟的记录被回收 |
| C4 | **收尾态不随组件卸载丢失** | 收尾中把坞面板关掉再打开 ⇒ 仍显示收尾态；收尾中刷新页面 ⇒ 首帧即收尾态 |
| E1 | **关机拓展**：其它插件登记的动作在关闭时真的执行 | 登记一条命令式钩子 ⇒ 用插件关闭 ⇒ 命令在**交棒之前**跑完（顺序可断言）；演练**不执行** |
| E2 | 关机拓展**失败不阻塞、超时被限** | 塞一条永不完成的钩子 + 一条抛错的 + 一条正常的 ⇒ 前两条记失败（含超时原因），第三条照跑、关闭流程照走 |
| E3 | 关机拓展**一次进程至多一次** | 主动关闭那一趟跑过的，在兜底那趟全部跳过；热重载/卸载（无信号）**不跑** |
| D1 | 全程**不丢未落盘事件** | 关闭前后比对会话日志的**字节数与末事件序号**（对照：强杀 vs 本流程双跑差分）。当前读数与局限见 §2.4 |

## 8. 实现依据（逐条已坐实，附证据行号）

> 这一节是给"改代码的人"核对的：每条契约都能追到平台源码的一处或一次实读。
> 保留 `文件:行` 是**刻意的**——删掉它这一节就失去可核对性。

1. ✅ **"拒绝进入"的收敛路径**：`dsh-agent-loop/lib/index.js:538-541` —— 决策为拒绝时置
   `turnEnds = { kind: 'blocked' }` 并**直接 `return false` 退出回合**；不抛错、**不触发回合停止事件**
   （它在 `:564-570`，位于 return 之后）。当前 step 已在 `:555` 正常跑完 ⇒ "停在安全边界"成立。
2. ✅ **监听器注册姿势**：`ctx.on('agent/pre-step', async (payload, next) => …)`，payload 为
   `{ agent, messages, turn, step, signal }`，`next()` 返回决策对象。官方 14 处插件同款用法。
3. ✅ **取消的副作用面**：`dsh-agent-loop/lib/index.js:405-411` —— 默认**清空收件箱**并中断当前 phase；
   `{ keepInbox: true }` 可保留。本插件只在用户点「立即停止」时调用，且依赖默认的清空语义
   （那些待办输入已在清单里以"丢弃条数"记账）。
4. ✅ **收尾态的取状态方式**：宿主自建只读状态接口供客户端轮询（不依赖长连接存活）；已实现并有离线判据。
5. ✅ **启动半区的平台原语**：客户端会话服务的"把某个会话选成当前会话"—— id 不在列表里会显式报错
   （fail loud，不是静默失败）⇒ 客户端必须自己判"会话还在不在"，并在失败时把键变成重试。
   会话列表读数还有一个"列表还没拉到"的阶段，此时**不能**据"查不到"断定会话被删。
6. ✅ **坞入口的角标只能在注册那一刻给**：面板按注册参数里的角标值画，坞自己的更新通道不在公开服务面上
   ⇒ 启动半区改成"**先读清单、再注册**"；接口读不到/超时（2s 上限）也照旧注册，**按钮不许迟到**。
7. ✅ **坞面板的内容节点每次打开都现造**：面板打开时先读条目再**新造**节点交给浮层 ⇒ 面板一关组件卸载。
   推论（见 §1.3）：**跨面板开关的持久状态必须住在模块里**。
8. ✅ **客户端半区的改动会被自动热换**：热换组件每 500ms 轮询产物（比 mtime+size），一变就推给浏览器侧换模块。
   只读核对办法：抓推送流里的产物地址比对关键字 ⇒ 宿主投递的就是新字节。
9. ✅ **「一键继续」= 投一条消息并唤醒驱动**（可行性论证 §1.1 对"继续"的定义）：
   宿主 `sessionController.resolveAgent(id)`（冷会话在这一步被恢复）→
   `agent.followup(createUserMessage({content, source:{kind:'safely-quit'}}))` →
   `sessions.flush(session)`。与平台自己的定时提醒（`dsh-schedule` 的 `source:{kind:'schedule'}`）同一条公开路。
   ⚠ **曾走错一版**：用平台的目标原语（`remote.goals.create/resume`）。它错在三处 ——
   ① 目标一武装，`dsh-goal-round-driver` 就会在 agent 空闲时**自己**开下一轮（默认上限 256 轮），
   那是无人值守的自动续跑（本规格 §1"不做"）；② 每个被关闭打断的会话都凭空多出一份**用户从没设过的持久目标**
   （`dsh-goal` README 自己写着"例行单轮工作不该建目标"）；③ 它虽然不产生 `kind:'user'` 的消息，
   但目标轮次的 prompt 本身就是一条 user 角色消息（只是来源标成 goal），"不产生用户消息"只是名义成立。
   客户端也因此不再需要任何目标接口 —— 它只送会话 id，消息由宿主造。
10. ✅ **框架的"拆卸事件"在本平台是死钩子**：事件表只有内部事件，全平台没有对应派发点；
    `on()` 对任意事件名只登记、不校验 ⇒ 写了不报错、**永不触发**。已有三处死代码踩在这上面。
    **唯一真实生效的清理面是"挂到 effect 上的析构器"。**
11. ✅ **异步析构会被 await，但全树共享一份 5 秒总预算**：框架并行跑各 fiber 的析构器（抛错被吞成日志，
    插件之间**没有确定先后**），并在拿到 in-flight promise 后等待 ⇒ 异步清理确实被等到；
    但平台的 5 秒超时是**整棵树 + 收尾代理的总预算**，计时器与拆卸**并发武装**，超时走硬退出（没有第二次机会）；
    第二次信号会立刻秒退。⇒ 本插件的兜底那趟预算因此定在 2500ms（§2.3），主动关闭那一趟不受此限（它在交棒之前）。
12. ✅ **平台没有任何"关机钩子"服务，这块生态位是空的**：对外提供面里只有"发起退出"与"启动就绪"与生命周期有关；
    唯一叫 shutdown 的机制是 SDK 的 RPC 方法，不面向插件。⇒ §2.3 的服务有明确的生态位。
13. ✅ **跨插件服务的既有惯例**：服务名可以带连字符；提供方用 `ctx.provide(name, service)`（重名会抛，
    因此提供前先探测）；消费方一律用"等晚到服务"的注入写法，**模块级依赖声明要留空**
    （写进去就是硬依赖，缺服务整包不加载）；未声明依赖时按属性直接访问会**抛**。
